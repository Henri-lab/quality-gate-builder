# 压测流水（load testing pipeline）

> 目标不是"压出最大 RPS"，而是回答三个问题：**当前能扛多少、瓶颈在哪、改了代码有没有劣化**。

## 1. 工具选型

| 工具 | 适合 | 理由 |
| --- | --- | --- |
| k6 | 首选（Go 栈团队） | 脚本即代码、原生阈值断言、CI 友好、`--summary-export` 机器可读 |
| Locust | Python 团队 | 代码定义行为分布，分布式压测成熟 |
| hey / wrk | 单点快速摸底 | 不适合业务剧本与断言 |
| Gatling | JVM 团队 | 企业报告丰富 |

默认推荐 **k6**：与"门禁可执行"目标最匹配，压测结果直接参与 CI 判定。

## 2. 流量模型（按目的选）

| 模型 | 用法 | 时长 | 关注 |
| --- | --- | --- | --- |
| smoke | 1~5 VU，确认脚本正确 | 1~2 分钟 | 0 错误 |
| load | 目标并发，验证基线 | 10~30 分钟 | p95/p99、错误率 |
| stress | 逐步加压找拐点 | 直到劣化 | 拐点前的吞吐、饱和信号 |
| spike | 突发（秒杀/回调洪峰） | 短时 | 限流/熔断是否生效 |
| soak | 长时间低负载 | 2~24 小时 | 内存泄漏、连接泄漏、日志膨胀 |

业务剧本 = 三个模拟器的流量版：支付回调洪峰、混合用户行为、完整订单流程（见 simulators.md）。

## 3. 指标与断言

必须断言（写进 k6 thresholds，超阈值即红）：

```js
export const options = {
  thresholds: {
    http_req_duration: ['p(95)<500', 'p(99)<1000'],
    http_req_failed: ['rate<0.01'],
    checks: ['rate>0.99'],
  },
  scenarios: {
    order_flow: { executor: 'ramping-vus', stages: [
      { duration: '2m', target: 50 }, { duration: '5m', target: 200 }, { duration: '3m', target: 0 }] },
  },
};
```

资源侧观测（与断言同权重）：CPU/内存/连接池使用率、DB 慢查询、outbox 积压、GC 停顿。
**只看接口延迟、不看资源与下游积压的压测没有意义**。

## 4. 基线（baseline）与门禁

建立基线流程：

1. 压测环境 = 生产同规格（或按比例折算并声明）；
2. 排除冷启动与首轮抖动，取 3 次的中位数；
3. 基线随版本归档（`perf/baseline-vX.Y.json`）；
4. 门禁容差：p95 ≤ 基线×1.2、错误率 ≤ 基线+0.5pp、吞吐 ≥ 基线×0.9——任一超出即红。

## 5. 常见误判

- 只报吞吐不报 p99/错误率；把"压测机自身瓶颈"当成服务上限；
- 压测与生产共用环境（打挂自己）；不清理压测产生的订单/账本数据；
- 限流/熔断在压测下被触发却当成 bug——先在剧本里声明期望行为；
- 一年压一次，平时没有持续回归（渐进劣化不可见）。
